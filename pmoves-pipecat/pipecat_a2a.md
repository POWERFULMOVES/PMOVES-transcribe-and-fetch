# Pipecat and Google A2A Protocol Integration: Findings and Recommendations

This document outlines findings from reviewing the Google Agent2Agent (A2A) protocol specification (primarily from `docs/A2A/docs/specification.md`) and provides recommendations for integrating your Pipecat agents within the `pmoves-pipecat/main.py` application for broader interoperability. It complements the existing internal `AgentCommand` protocol (detailed in `masterplan/AGENT_COMMAND_PROTOCOL.md`) by focusing on external A2A compliance.

## 1. Core A2A Concepts (Summary from `docs/A2A/docs/specification.md`)

The A2A protocol is designed for interoperability between AI agents. Key aspects include:

*   **Transport:** HTTP(S) with JSON-RPC 2.0 as the payload format.
    *   Reference: `docs/A2A/docs/specification.md#3-transport-and-format`
*   **Agent Discovery (`AgentCard`):**
    *   A JSON metadata document (typically `/.well-known/agent-card.json`; legacy alias `/.well-known/agent.json`) describing an agent server.
    *   Key Fields: `name`, `description`, `url` (the A2A JSON-RPC service endpoint), `version`, `provider`, `capabilities` (e.g., support for streaming, push notifications), `authentication` (schemes required to call the agent), and `skills` (specific functions the agent offers).
    *   Reference: `docs/A2A/docs/specification.md#5-agent-discovery-the-agent-card` and `docs/A2A/docs/specification.md#55-agentcard-object-structure`.
*   **Interaction Model (`Task`):**
    *   The `Task` object is the fundamental unit of work, identified by a unique ID.
    *   Tasks have a lifecycle managed by `TaskState` (e.g., `submitted`, `working`, `input-required`, `completed`, `failed`).
    *   Reference: `docs/A2A/docs/specification.md#61-task-object` and `docs/A2A/docs/specification.md#63-taskstate-enum`.
*   **Communication Content (`Message` and `Part`):**
    *   `Message` objects represent a communication turn, having a `role` (`"user"` or `"agent"`) and containing one or more `Part` objects.
    *   `Part` objects carry the actual content and are a discriminated union. Common types:
        *   `TextPart`: For plain text (`type: "text"`).
        *   `FilePart`: For files (`type: "file"`), containing a `FileContent` object (which can hold data as `bytes` (Base64) or a `uri`).
        *   `DataPart`: For structured JSON data (`type: "data"`).
    *   Reference: `docs/A2A/docs/specification.md#64-message-object` and `docs/A2A/docs/specification.md#65-part-union-type`.
*   **Agent Outputs (`Artifact`):**
    *   Tangible outputs generated by an agent (e.g., documents, images).
    *   Composed of one or more `Part` objects.
    *   Reference: `docs/A2A/docs/specification.md#67-artifact-object`.
*   **JSON-RPC Methods:**
    *   Standardized methods for interacting with an A2A server. Key methods include:
        *   `tasks/send`: Initiates a new task or sends a message to an existing one. For synchronous request/response or client-side polling.
        *   `tasks/sendSubscribe`: Similar to `tasks/send` but establishes a Server-Sent Events (SSE) stream for real-time updates. Requires `AgentCard.capabilities.streaming: true`.
        *   `tasks/get`: Retrieves the current state of a task.
        *   `tasks/cancel`: Requests cancellation of an ongoing task.
        *   `tasks/pushNotification/set` & `tasks/pushNotification/get`: Manage server-to-client push notifications for task updates.
    *   Reference: `docs/A2A/docs/specification.md#7-protocol-rpc-methods`.

## 2. Current State of `pmoves-pipecat/main.py` A2A Implementation

*   **Discovery:** The `/a2a/discover` endpoint serves a custom JSON structure, not a standard A2A `AgentCard`.
*   **Messaging:** The `/a2a/message/{agent_id}` endpoint is a simple HTTP POST. It does not use JSON-RPC 2.0, nor does it conform to the A2A `Task`, `Message`, or `Part` object structures.
*   **SDK/Library:** The `ImportError: No module named 'agent2agent_protocol'` indicates that a necessary A2A SDK or a custom module providing A2A functionalities is missing or not correctly installed/referenced.

## 3. Key Recommendations for A2A Conformance

To make your Pipecat agents A2A-compliant, consider the following steps:

### 3.1. Adopt an A2A SDK
*   **Why:** Implementing the full A2A object model (Tasks, Messages, Parts, AgentCards, etc.) and JSON-RPC 2.0 request/response handling from scratch is complex and error-prone. An SDK will provide these structures (often as Pydantic models or dataclasses) and helper utilities.
*   **Suggestions:**
    *   Look for an official SDK from Google if available (e.g., `a2a-sdk` if it exists for Python).
    *   Explore community-driven Python A2A libraries like `python-a2a` (by themanojdesai, found during web searches).
*   **Action:** Choose a suitable SDK, add it to your project dependencies (e.g., `requirements.txt`), and install it. This should resolve the `agent2agent_protocol` import error.

### 3.2. Implement Standard Agent Discovery
*   **What:** Expose an endpoint that serves a valid A2A `AgentCard` JSON document.
*   **Where:** The recommended location is `/.well-known/agent-card.json` (keep `/.well-known/agent.json` as a legacy alias). Your FastAPI application should serve this.
*   **Content:** The `AgentCard` should accurately describe your Pipecat agent service:
    *   `name`, `description`, `version`.
    *   `url`: The URL of your new A2A JSON-RPC endpoint (see 3.3).
    *   `provider`: Information about your organization.
    *   `capabilities`: Specify if you support `streaming` (for `tasks/sendSubscribe`) or `pushNotifications`. Initially, you might set these to `false`.
    *   `authentication`: Define any authentication schemes required to call your A2A service (e.g., "Bearer" for API tokens in the `Authorization` header).
    *   `skills`: Define the specific capabilities your Pipecat agent(s) offer. Each skill needs an `id`, `name`, `description`, and can specify `inputModes` (MIME types it accepts, e.g., `["text/plain"]`, `["image/png"]`) and `outputModes`.
*   **Reference:** `docs/A2A/docs/specification.md#5-agent-discovery-the-agent-card` and the sample AgentCard.

### 3.3. Refactor A2A Communication Endpoint
*   **What:** Replace the current custom `/a2a/message` endpoint with a single endpoint that handles A2A JSON-RPC 2.0 requests.
*   **Example Endpoint Path:** `/a2a/rpc` or `/a2a/v1`.
*   **Functionality:** This FastAPI endpoint (using `POST`) will:
    1.  Receive the `JSONRPCRequest` object in the HTTP request body.
    2.  Inspect the `method` field (e.g., `"tasks/send"`, `"tasks/get"`).
    3.  Dispatch to a corresponding handler function for that method.
    4.  The handler function will process the request according to A2A specifications.
    5.  Return a `JSONRPCResponse` object.
*   **Initial Methods to Implement:**
    *   `tasks/send`: To receive messages/tasks.
    *   `tasks/get`: To allow clients to poll for task status.
*   **Reference:** `docs/A2A/docs/specification.md#7-protocol-rpc-methods` and `docs/A2A/docs/specification.md#611-json-rpc-structures`.

### 3.4. Adapt Pipecat Agent Interaction Logic

#### 3.4.1. Processing Incoming A2A Messages (e.g., in `tasks/send` handler)
1.  **Parse `TaskSendParams`:** The `params` of a `tasks/send` request will be a `TaskSendParams` object.
2.  **Extract A2A Message:** Get the `Message` object from `params.message`.
3.  **Convert `Parts` to Pipecat `Frames`:** Iterate through `message.parts`:
    *   If `part.type == "text"`, create a Pipecat `TextFrame(text=part.text)`.
    *   If `part.type == "file"` (e.g., for an image):
        *   Access `part.file`.
        *   If `part.file.bytes` (Base64 encoded content) is present, decode it.
        *   Create a Pipecat `ImageRawFrame(data=decoded_bytes, format=...)` (determine format from `part.file.mimeType`).
    *   If `part.type == "data"`, `part.data` will be a JSON object/array. Your Pipecat agent logic needs to know how to handle this based on the invoked skill.
4.  **Send Frames to Pipecat Agent:** Use your existing mechanism (e.g., `agent_instance.queue_frame_for_processing()`) to pass these frames to the appropriate Pipecat agent instance. You may need a system to map an A2A `task.id` to a specific Pipecat agent instance or session.

#### 3.4.2. Formatting Pipecat Agent Output as A2A Response
1.  **Receive Output Frames:** Get the output frames from your Pipecat agent (e.g., from your `OutputQueueProcessor`).
2.  **Convert Pipecat `Frames` to A2A `Parts`:**
    *   For a Pipecat `TextFrame`, create an A2A `TextPart`.
    *   For a Pipecat `ImageRawFrame`, Base64 encode the image data and create an A2A `FilePart` with the bytes and `mimeType`.
3.  **Construct A2A `Message` and/or `Artifacts`:**
    *   Bundle the generated `Part` objects into an A2A `Message` with `role: "agent"`. This can be placed in `Task.status.message`.
    *   If the agent produces distinct outputs, create `Artifact` objects, each containing relevant `Part`s, and add them to `Task.artifacts`.
4.  **Create/Update `Task` Object:**
    *   Populate a `Task` object with the `id` from the original request, the new `status` (e.g., `state: "completed"` or `"failed"`), the agent's response message, and any artifacts.
5.  **Return `JSONRPCResponse`:** The `Task` object becomes the `result` in the `JSONRPCResponse`.

### 3.5. Task State Management
*   Your A2A server will need to maintain the state of tasks (identified by `task.id`). For `tasks/get` to work, and for `tasks/send` to potentially update existing tasks, you'll need a way to store and retrieve `Task` objects (in-memory for simplicity, or a database for persistence).

### 3.6. (Future Consideration) Streaming with `tasks/sendSubscribe`
*   Supporting `tasks/sendSubscribe` for real-time updates via Server-Sent Events (SSE) is a more advanced feature.
*   It would require:
    *   Your Pipecat pipeline processing to be fully asynchronous.
    *   Your FastAPI A2A endpoint to manage SSE connections.
    *   As your Pipecat agent generates output frames incrementally, you would send `TaskStatusUpdateEvent` or `TaskArtifactUpdateEvent` objects over the SSE stream.
*   **Reference:** `docs/A2A/docs/specification.md#72-taskssendsubscribe`.

### 3.7. Integrating Internal `AgentCommand` with Google A2A
While the Google A2A protocol defines the structure for inter-agent communication (`Task`, `Message`, `Part`), your existing internal `AgentCommand` structure (see `masterplan/AGENT_COMMAND_PROTOCOL.md`) can still be utilized.

*   **Encapsulation:** Internal `AgentCommand` objects (serialized as JSON) can be embedded within the `data` field of an A2A `DataPart` (`type: "data"`).
    *   The A2A `Message` would still adhere to the Google A2A specification.
    *   The `Skill` definition in the `AgentCard` should indicate that the expected `DataPart` contains a PMOVES `AgentCommand`.
*   **Benefits:** This approach allows leveraging your established internal command processing logic within Pipecat agents while using Google A2A as the standardized transport and discovery mechanism for external interactions.
*   **Considerations:**
    *   The receiving agent must be aware of this encapsulation and know how to parse the `AgentCommand` from the `DataPart`.
    *   This is suitable when a Google A2A `Skill` directly maps to an internal agent capability triggered by an `AgentCommand`.

## 4. Conclusion

**Note on Current A2A Implementation Status:**
The `masterplan/PMOVES_AGENT_PLATFORM_PLAN.md` indicates A2A protocol support as "Enhanced Core Service Implementation: [x] A2A protocol support for agent-to-agent communication", while `PIPECAT_ARCHITECTURE.md` lists "a2a_available: false" in its health response example and refers to the A2A endpoints in `pmoves-pipecat` as not conforming to the Google A2A specification. The recommendations in this document serve as the definitive guide to achieve full Google A2A protocol compliance, bridging this gap and aligning with the goal of robust inter-agent communication.

Aligning `pmoves-pipecat/main.py` with the A2A protocol specification will significantly enhance its interoperability. The recommended approach is to:
1.  Integrate a robust A2A Python SDK.
2.  Implement the `AgentCard` for discovery.
3.  Overhaul the communication endpoint to support JSON-RPC 2.0 and the defined A2A methods (starting with `tasks/send` and `tasks/get`).
4.  Adapt the data conversion logic between A2A `Message`/`Part` structures and Pipecat `Frame` objects.

This will provide a solid foundation for your agents to communicate effectively within a broader A2A ecosystem.
